# commit-changes

변경사항을 의미 단위로 나누고, 컨벤션에 맞는 메시지로 커밋한다.

## 1단계: 포맷 정리 및 변경사항 확인

이 프로젝트는 git hook(pre-commit/commit-msg)을 쓰지 않는다. 대신 커밋 단위를 나누기 전에 Spotless로 포맷을 먼저 정리한다. (나눠서 stage한 뒤에 포맷하면 포맷 변경이 다시 섞인다)

- 현재 브랜치가 `main` 또는 `develop`이면 직접 커밋하는 게 맞는지 사용자에게 확인받는다. (막지는 않는다)
- `./gradlew spotlessApply`로 `origin/develop` 대비 변경된 Java 파일의 포맷(google-java-format, 미사용 import 제거, 트레일링 공백 등)을 정리한다. (`build.gradle`의 `ratchetFrom 'origin/develop'` 설정)
- `git status`로 전체 변경 파일을 파악한다. 수정된 파일뿐 아니라 새 파일(untracked)도 여기서 확인한다.
- 내용은 `git diff`(unstaged), `git diff --staged`(staged)로 확인한다. 새 파일은 diff에 나오지 않으므로 파일을 직접 읽는다.
- 의도치 않게 포함된 파일이 있는지 확인한다. (`.env`, 임시 파일, 디버그용 로그 등)
- 발견되면 커밋에서 제외하고 사용자에게 알린다.

**실패 유형별 대응**

- **`spotlessApply`로 해결되지 않는 문제(컴파일 에러 등)**: 에러를 정리해 사용자에게 보고하고, 수정 방향을 제안하되 임의로 코드를 고치지 않고 확인을 받는다.

## 2단계: 커밋 단위 분리

- 하나의 커밋 = 하나의 목적을 기준으로 나눈다.
- 예: "API 추가"와 "마이그레이션 추가"가 섞여 있으면 커밋 2개로 분리한다.
- 단위를 나누기 애매하면 사용자에게 확인받는다.

## 3단계: 커밋 메시지 작성 및 커밋

`docs/commit-convention.md`를 읽고 커밋 컨벤션을 따른다. 커밋 메시지 형식을 자동으로 검사하는 도구가 없으므로, 규칙을 직접 확인하며 작성한다.

## 완료 후

- 생성된 커밋 목록(해시, 메시지)을 요약해서 보고한다.
- push는 사용자 확인 후 진행한다. (자동으로 push하지 않음)
